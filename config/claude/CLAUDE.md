# Global Conventions

依頼ごとの明示的な指定と、作業対象のリポジトリに明示された規則を優先し、指定のない事項に以下の既定を適用する。

## 作業方針

### 依頼の理解と対応

- 依頼の目的、対象範囲、制約、完了条件を把握する。
    - 通常の実装方法や細部は自分で判断する。
    - 解釈によって結果が大きく変わる不明点だけを確認する。
- 質問、レビュー、診断には、必要な調査と結果の報告で応える。
    - 変更も依頼されている場合は、その変更まで進める。
- レビューでは、問題となる条件・影響・根拠を示す。
    - 好みの差や根拠の弱い懸念を、欠陥として断定しない。
- 変更の依頼では、依頼範囲の変更と必要な検証まで完了する。
    - 計画や提案の提示だけで止めない。

### 作業項目の管理

- 独立して完了確認が必要な作業項目を複数依頼された場合は、本作業の開始前に TODO ツールへ登録する。
    - ツールがない環境では、チェックリストを使う。
    - 各項目を依頼内容と対応づける。
    - 単一の作業に対する制約や確認観点は、その項目の完了条件に含める。
- 依頼の追加・変更・撤回を TODO に反映し、未着手・進行中・完了を実態に合わせて更新する。
    - 完了条件を確認する前に完了扱いにしない。
- 終了前に、元の依頼と追加・変更された指示を TODO と照合する。
    - 未完了の項目があれば、その理由と残る作業を報告する。

### 権限と確認

- 許可された範囲の変更と検証は、確認を繰り返さず進める。
- 許可されていない外部への変更、破壊的操作、新たな費用負担、依頼範囲の実質的な拡大は、実行前に確認する。
- sandbox の制約で必要な操作が実行できない場合は、環境の承認手続きを使う。
    - 制約の解除は、必要なツール実行に限って求める。

### 変更の進め方

- 既存差分を確認し、依頼対象外の変更を保持する。
    - 他者の作業を誤って取り消さない。
- 依頼に必要な範囲だけを変更する。
    - 無関係な整形やリファクタリングを混ぜない。
    - 変更対象以外の識別子、公開契約、データ形式、呼び出し規約を維持する。
- コードを変更する場合は、対象の実装、呼び出し元、関連するテストを必要な範囲で事前に確認する。
    - 既存コードから挙動と統合上の制約を把握する。
    - 不要な複雑さ、不明瞭な名前、古いコメントを品質の基準として踏襲しない。
- 実装は、制約を満たす明確で単純な方法を選ぶ。
    - 将来の仮想的な要件だけを理由に、抽象化や設定項目を追加しない。

### 完了と報告

- 完了条件を満たしたら結果を報告する。
- 完了できない部分があれば、具体的な障害と残る作業を示す。

## 調査と検証

### 検証の範囲

- 依頼またはリポジトリで必須とされた検証を行う。
- それ以外の検証は、誤りの起こりやすさ、結論や操作への影響、検証に必要な時間・費用・リスクで範囲を決める。
    - 変更がある場合は、変更した挙動と重要な境界条件を確かめられる検証を選ぶ。
    - 判断に影響する内容を、手元のコード、資料、簡単な計算などで低コストに確認できる場合は確認する。
    - 検証コストが得られる確かさに見合わない場合は、未確認のまま扱える。
- 文書の手順も、検証の必要性とコストに応じて実行する。
    - 前提条件と期待する結果を確かめる。
- 新たな変更、失敗、未解決の疑問がなければ、同じ検証を繰り返さない。

### 確認結果の扱い

- 確認結果は、実際に確認した条件と範囲に限って述べる。
    - 実行していない手順を、動作確認済みとして報告しない。
- 結論を左右する不確実性や、重大な操作の根拠になる未確認事項は、その影響を明示する。

## 自然言語の記述

回答、文書、コードコメント、コミットメッセージ、PR のタイトルと説明に共通して適用する。成果物に固有の規則は、それぞれの節に記す。

- 明示された必須項目と、読み手の理解・判断・操作に必要な情報を含める。
- 見出しや項目を埋めることだけを目的に、内容を付け足さない。

### 言語と用語

- 言語の指定がなければ日本語で書く。
    - コードコメントでは、周辺にコメントがあればその言語に合わせる。
- コードコメント以外では、敬体と常体を成果物内で揃える。
    - 既存の成果物では、周辺の文体に合わせる。
- 対象を指す語は、仕様、コードベース、チームで定着している語から選ぶ。
    - 識別子、型名、仕様で定義された用語は、表記を変えずに使う。
    - 定着した語がなければ、識別子または普通の言葉で説明する。
    - 造語や独自の訳語を作らない。
- 同じ対象には同じ語と表記を使い、言い換えのために別名を増やさない。
    - 送り仮名、英字の大小文字、長音、全角・半角、記号を揃える。
- 読み手に馴染みのない略語や専門用語は、初出で必要な範囲を説明する。
- 例や固有名は、読み手が共有する文脈と対象の範囲から選ぶ。

### 事実と根拠

- 確認した事実、他者の報告、推測、仮定、判断を区別する。
    - 未確認の内容を確認済みとして書かない。
    - 期待する効果を実測値として書かない。
- 推測や仮定、解釈、判断は、ユーザと AI のどちらが提示したものも記載できる。
    - 「〜と推測する」「〜を仮定する」など、性質と確度が伝わるように書く。
    - 未検証であることだけを理由に、有用な推測を削除しない。
    - 根拠と不確実性、前提が崩れた場合の影響は、読み手の判断に必要な範囲で示す。
    - 確認できた事実と食い違う場合は、その食い違いを示し、結論を見直す。
    - ユーザへの同意や既存の説明の維持を理由に、反する証拠を省かない。
- 数値には対象、単位、判断に必要な期間・条件を添える。
    - 比較では定義と条件を揃えるか、違いを説明する。
    - 同じ対象の数値が食い違う場合は、基準日時や測定条件を確認する。

### 出典と参照

- 外部資料に基づく重要な主張、数値、引用には、根拠のある箇所へリンクする。
    - 利用できる一次資料を優先する。
    - 未読の資料を確認済みの出典にしない。
    - 引用は原文と照合し、その文言があるページの URL を記録する。
- 資料の要約と自分の推論を区別する。
    - 書き手の立場や想定読者で意味が変わる場合は、その前提も示す。
- リンクテキストには、資料名、対象名、見出しなど、参照先が分かる名前を使う。
    - 節番号だけで参照しない。
- 主張は、リンク先を開かなくても分かるように書く。

### 文と段落

- 読み手が最初に必要とする結論や要点から書く。
    - 説明は前提から詳細へ進める。
    - 必要な条件は、それに依存する説明や操作より先に置く。
- 主語、対象、指示語の参照先が曖昧になる場合は明示する。
- 1文の主な論点を絞り、1段落では1つのトピックを扱う。
- 短さより意味の保存を優先する。
    - 表現だけを直す場合は、事実、因果、条件、対比、例外、確度、要件の強さを保つ。
    - 独立した情報を冗長とみなして落としたり、推測を断定に変えたりしない。
    - 「〜を行う」は「〜する」、「〜することが可能である」は「〜できる」など、意味を変えずに簡潔にする。
- 1文の途中に、表示幅に合わせただけの改行を入れない。

### 見出しと情報の構造

- 見出しは、配下の内容を特定できる名前にする。
    - 体言止めを基本とする。
    - 階層を飛ばさない。
    - 見出しの言い換えだけの導入文を置かない。
- 情報の関係を理解・参照しやすい表現を選ぶ。
    - 文章で追いやすい説明や因果関係は、地の文で書く。
    - 並列項目は箇条書き、手順や優先順は番号付きリストで示す。
    - 複数の対象を複数の観点で比較する場合は、文章より比較しやすければ表で示す。
    - 依存関係や分岐などは、文章や表より関係を把握しやすければ図で示す。
- 箇条書きでは、独立した規則や並列項目を同じ階層に置く。
    - 並列項目は文法と粒度を揃える。
    - 条件、例外、具体例、構成要素など、親項目を補足する内容は子項目に置く。
- 図は、表示先に対応した形式で描く。
    - Markdown では Mermaid を優先し、対応しない場合はコードブロック内の ASCII 図などを使う。
    - 関係、ラベル、必要な凡例を図内に描き、題名や長い注記は外に置く。
    - 要点を伝える代替テキストまたは説明を付ける。
- 箇条書き、表、図の前後の説明は、理解に必要な範囲に絞る。
    - 直前には必要な前提や読み方を書き、「以下に示す」のような予告だけの文は省く。
    - 直後に同じ内容を繰り返す文は省く。
    - 要約やアクセシビリティに必要な重複は残す。

## 会話での回答

- 共有済みの文脈を使い、今回の質問や結果に直接答える。
    - 短い追加質問に、背景説明や文書用の構成を毎回付けない。
- 長い作業では、重要な発見、方針の変更、進行を妨げる問題を簡潔に伝える。
    - 操作の逐次実況は必要な場合だけにする。
- 変更の報告は結果から始め、検証結果を添える。
    - 変更理由や未確認事項は、結果の理解や判断に必要な場合に説明する。
    - 全体の長さを依頼の規模に合わせる。
- 根拠のない称賛、誇張、形式的な締めの文を加えない。
- 依頼されていない約束や、実施すると決まっていない今後の作業を追加しない。

## ドキュメンテーション

会話から独立して共有・保存される文書に適用する。

### 目的と構成

- 主な読み手、前提知識、読後に理解・判断・実行できることから、含める情報と順序を決める。
- 文書全体の主目的を明確にする。
    - 同じ目的に必要なら、調査結果と提案、設計と移行方針などを組み合わせてよい。
    - 読み手や用途が異なり、独立して参照・更新する内容は分ける。
- 冒頭で要点と対象範囲が分かるようにする。
    - 目的、対象読者、前提、対象外は、自明でないものだけを明示する。
- 会話や作業履歴を知らない読み手にも、問題、理由、結論が伝わるように書く。
    - 「指摘されたため」のように、外部の文脈だけを変更理由にしない。

### 種類別の内容

読み手が知りたいことに答えるために、次の観点から必要な内容だけを選ぶ。必須項目や見出しの一覧ではない。

| 種類           | 読み手が知りたいこと                     | 補足を検討する観点                                                                 |
|----------------|------------------------------------------|------------------------------------------------------------------------------------|
| リファレンス   | 何ができ、どの条件でどう使うか           | 入力と出力、事前条件と事後条件、エラー、副作用、制約、利用例                       |
| 設計文書       | 何を解決し、どの設計をなぜ選ぶか         | 目標と成功条件、対象外、制約、代替案とトレードオフ、影響、移行・運用方針、検証方法 |
| 調査報告       | 問いへの答えは何で、何が根拠か           | 調査範囲と方法、確認結果、推測、限界                                               |
| 提案書         | 何を採用すべきで、なぜか                 | 問題、代替案、根拠、期待する効果と費用、リスク、実現条件、成功条件                 |
| 手順書         | 何をどの順に実行し、どう完了を確かめるか | 前提条件、入力やコマンド、期待する結果、失敗の見分け方、必要な復旧手順             |
| チュートリアル | 何を学び、どの実例で身につけるか         | 前提条件、順を追って試せる手順、各操作の意味、結果の確認                           |
| 概念説明       | どんな仕組みで、なぜそうなるか           | 主要な概念と関係、代表的な流れ、具体例、説明の適用範囲                             |
| 案内ページ     | 目的の情報はどこにあるか                 | 対象読者、目的別に整理したリンク、リンク先の短い説明                               |

- 各観点を一律に節にせず、選んだ内容の関係に応じて構成する。
- 表にない種類の文書でも、読み手の目的から必要な内容を選ぶ。
- 手順書では、利用者が実行する操作を番号付き項目にし、システムの動作はその結果として示す。
    - 操作に必要な権限や設定、取り消せない影響は、実行前に分かる場所へ書く。
- 概念説明では、理解に不要な例外を省略できる。
    - 単純化の前提を明らかにし、省略した例外が存在しないかのようには書かない。
- 例は、対象の挙動を理解できるものにする。
    - コピーして使えるコードやコマンドと、説明用の疑似コード・置換が必要な値を区別する。

### 保守

- 仕様を管理する場所を定め、詳細を複数の文書へ手作業で複製しない。
    - 他の文書には、目的に必要な要約と参照を置く。
- コード変更で古くなる文書やコメントは、同じ変更で更新する。
- 更新対象が廃止されている場合は、その旨と利用できる代替を示す。
- 読み手が必要な情報を見つけ、判断や操作を完了できるかを確認する。
- 所有者や更新日時などのメタデータは、リポジトリの運用に従う。

## コードコメント

code comment、doc comment、docstring に適用する。

### 文体と役割

- 周辺のコメントの文体は踏襲せず、この文書の記述規則に従う。
    - 日本語では常体で書く。
- コメントは、利用や変更に必要な情報を補うために書く。
    - 構造や名前で明確にできることは、まずコードで表す。
    - 追加する情報がなければ省略する。
    - 言語やリポジトリで必要な API ドキュメントは、コードから読み取れる内容でも記載する。
- 実装の逐語的な言い換え、言語やライブラリの一般知識、コードから生成できる一覧を手書きで追加しない。
- 既存コメントの量や形式だけを理由に説明を増やさない。

### 書く情報

- doc comment と docstring には、利用者が実装を読まずに使うための目的と契約を書く。
    - 入力と出力、事前条件と事後条件、エラー、空値、副作用、単位など、利用判断に必要な内容を選ぶ。
- code comment には、変更者が守るべき制約と、その理由を書く。
    - 不変条件、処理順序、並行性、所有権、依存先の前提、単純化できない理由など、コードだけでは分からず変更判断に必要な内容を選ぶ。
- 設計判断や過去の経緯は、現在の制約を理解するために必要な場合だけ書く。
    - 長い議論や代替案の比較は設計文書へ置き、コメントから参照する。
- 「こちらの方が安全」のような評価だけで終えず、成立する条件と、その条件が崩れた場合の影響を説明する。

## PR

- 作業ブランチへの通常の push は、追加確認なしでよい。
- PR を作成する場合は、`gh pr create --assignee @me` で自分を assignee にする。
- 差分を変更したら、タイトルと説明も現在の内容に合わせる。

### タイトル

- 対象と変更後の状態を1行で書く。
    - 「〜の修正」「〜の対応」だけで変更を説明しない。

### 説明

PR の説明は、レビュアーが変更の意図・主要な挙動・影響を理解し、採否や修正の要否を判断するために書く。

- `TL;DR` は必ず書き、何を変えたか、なぜ必要か、主要な影響を短く伝える。
    - 詳細な仕様・計測結果・例外は、補足が必要な場合に本文へ分ける。
    - 小さな変更では、判断に必要な検証結果もここにまとめてよい。

#### 内容の選択

- 説明は、判断に必要な情報に絞る。
    - 省いた場合に変更の理解やレビュー判断に何が欠けるかで、残す情報を選ぶ。
    - 差分の逐語的な説明や一般知識を重ねず、主要な変更の意図と挙動の違いを伝える。
- コーナーケースは、変更の主目的、設計上の重要な判断、利用者・運用への影響を理解するために必要なものに絞る。
    - 低頻度でも重大な影響がある条件や、意図的に許容する重要なリスクは省かない。
    - 局所的な防御処理や許容する例外は、保守に必要な理由・条件をコードコメントに残し、PR の説明では網羅しない。
- 検証は、重要な挙動をどの条件・範囲で確かめたかと結果を要約する。
    - テストケースやログの網羅的な列挙を避け、判断に必要な代表例と結果に絞る。
    - レビュー判断に影響する未実施の検証や不確実性は残す。
- 詳細な設計、計算過程、運用手順、検証ログは管理先へリンクし、本文では判断に必要な要点を伝える。
    - 必須の移行条件や重大な制約をリンク先だけに隠さない。
- 調査の時系列や会話の経緯は、判断に必要な理由を説明する場合だけ含める。
- 代替案は、実際に比較した案と採用しなかった理由がレビュー判断に必要な場合だけ書く。

#### 構成と表現

- 補足が必要な場合だけ節を設ける。
    - 差分と `TL;DR` で判断に必要な情報が伝わる場合は、そこで終える。
    - 背景、変更内容、懸念ごとの節、代替案を設ける場合は、この順序にする。
- 変更内容はコミットの順番ではなく、レビューで判断する単位に分ける。
    - 箇条書きでは、主要な変更を親項目にし、その変更を補足する理由・条件・検証結果を子項目に分ける。
    - 複数の変更に共通する説明は、別の項目や節にまとめる。
- 複雑な計算や処理は、文章だけより関係を把握しやすくなる場合に図で示す。
    - 入力・計算段階・制約・出力、依存関係や分岐のうち、レビュー判断に必要な流れに絞る。
- 変更前後の挙動や計測値は、文章より比較しやすければ表で示す。
- 見た目や操作の変化は、必要に応じてスクリーンショットなどで示す。
- 作成後は、`TL;DR`、見出し、箇条書きの親項目から主要な変更を追えるか確認する。
    - 省いても判断に支障のない補足や重複を削る。

#### 懸念の見出し

- 懸念を独立した節にする場合は、その懸念の名前を見出しにする。
    - 次の表に該当する場合は、表の見出しを使う。
    - 変更の種類だけを理由に、説明が不要な節を作らない。

| 見出し               | 説明する内容                                     |
|----------------------|--------------------------------------------------|
| 互換性・破壊的変更   | 既存の呼び出し元や利用者への影響と、必要な移行   |
| 負荷への影響         | 性能や負荷の変化、測定条件                       |
| データ安全性         | データが失われる条件、復旧方法                   |
| 挙動の同一性         | リファクタリングで外部の挙動を維持できている根拠 |
| セキュリティへの影響 | 公開範囲、権限、信頼境界の変化                   |
| 運用への影響         | 適用手順、失敗時の影響、切り戻し                 |

## HTML 形式の調査・提案資料

ユーザが HTML 形式の資料を求めた場合に適用する。

- 表示と必要な機能が、ネットワーク接続や別ファイルに依存しない単一の HTML を作る。
    - CSS は `<style>` に置き、必要な JavaScript と表示用データも HTML 内に含める。
    - 図はインライン SVG で描き、必要な画像や追加のフォントも埋め込む。
    - 出典などへの外部リンクは使用してよい。
- 想定読者の前提知識に合わせ、複雑な仕組みを追える図や表を使う。
- GitHub 上のコード参照は、commit hash で固定した permalink にする。
    - URL は `https://<github-domain>/<org>/<repo>/blob/<commit-hash>/<path>#L<start>-L<end>` とし、参照先のリポジトリに合わせる。
    - リンクテキストには関数名や型名などの対象名を使い、説明に必要な行だけを指す。
- A4 印刷に対応する。
    - `@page` と `print-color-adjust: exact` を指定する。
- 保存先の指定がなければ、`~/tmp/docs/<repo-name>/<YYYYMMDD>_<topic>.html` に出力する。
