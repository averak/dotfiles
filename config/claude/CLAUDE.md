# Global Conventions

## コード

- 既存コードの命名・構造・イディオムに合わせる。
- 周辺と読み比べて違和感のない記述にし、独自スタイルを持ち込まない。

## 自然言語

- **対象**: code comment / doc comment / docs files / PR title / PR description など、コード以外のすべての自然言語。日本語で書く。
- **前提**: 読み手は読まず、走査する。結論を先に置き、削り、主観を混ぜない。

### 語彙 — 名前を発明しない

- 対象を指す語は、コードベース・仕様・チームが既に使っている語から取る。識別子・型名・仕様上の用語をそのまま書く。
- 既存の語が無くても造語も訳語の創作もしない。識別子をそのまま出すか、その対象が何をするかを普通の言葉で書く。

### 文 — 1文に1論点

- 1文は1つの論点だけを述べる。原因と結果を1文に圧縮せず、ので・一方・ただし等で繋いで流れを示す。
- **文の中に列挙が埋まっていたら箇条書きに出す**。長い文の中の「A と B と C」「X または Y」が合図。
- 主語を省略せず「誰が何をしたか」を書く。日本語は主語が落ちても文が成立するので、意識して補う。
- 冗長な言い回しを削る。「〜を行う」→「〜する」、「〜することが可能である」→「〜できる」。
- 1文の途中で改行しない。ただし禁じているのは幅に合わせた折り返しであって、段階を追う論点を番号付きに開くことではない。

### 段落 — 冒頭文が論点を担う

- 冒頭の1文でその段落の論点を言い切る。読み手は冒頭文しか読まないことがある。
- 1段落1トピック。関係しない文は別の段落へ移すか消す。
- 3〜5文を目安にする。長すぎると読まれず、1文の段落が続くと流れが切れる。

### 構造 — 箇条書き・表・図をいつ使うか

- **箇条書き**: 並列な項目の列挙。順序に意味がなければ `-`、手順や優先順なら `1.`。項目の文法・粒度・語尾は揃える。
- **箇条書きにしない**: 因果や条件の説明、項目が1つのもの、地の文で流れを示すべきところ。説明を機械的に割ると読みにくくなる。
- **表**: 2軸以上の比較。列ヘッダは中身を名指しし、1セルは2文まで。
- **図**: 順序・分岐・依存など、文では追いにくい関係。mermaid を優先し、表しづらい場合のみ ASCII 図を ``` で囲む。
- 箇条書き・表・図の直前に、それが何を示すかの1文を置く。示したことを地の文で言い直さない。
- 見出しは中身を名指しする。開くまで中身が分からない見出しを付けない。

### 語調 — 事実だけを書く

- 誇張・主観 (「大幅に」「非常に」) を使わない。事実と数値で示す。
- 測っていないことを断定しない。確認した範囲と、していない範囲を書き分ける。
- 指示されていない依頼・約束・宣言を足さない。
- 数値には、それが何を示すかを併記する。測定条件 (期間・サンプリング・除外) は、知らないと結論の意味が変わる場合だけ書く。
- 敬体と常体を混ぜない。

### 内容 — why だけを書く

- 書く: 非自明な契約 (どんな入力でエラーか、空値で何が起きるか)、採用しなかった代替案、不変条件・順序・並行性・落とし穴、慣用的でない書き方の理由 (読み手が「単純化できる」と誤解して壊すのを防ぐ)。
- 書かない: 識別子・シグネチャ・実装をなぞる説明、コード変更で腐るリスト (subcommand 一覧、フィールド名一覧など)。

**why であっても下記は書かない。**「why だから書いてよい」は成立しない。事実として正しく、かつ非自明に見えるコメントほどこの罠にかかる。

- **一般論・教科書的事実**: その言語 / DB / ライブラリを使う人なら誰でも知っていること。例:「トランザクションを分けると読み取り時刻がずれる」。
- **済んだ経緯**: 「以前は逐次で遅かったのでこうした」。PR description の領分。ただしその経緯が今も編集を縛るなら、経緯ではなく制約として書く。履歴は読まれないが、その場のコメントは読まれる。
- **依存先の設計解説**: そのライブラリがなぜそう作られているか。ただし、呼び出し側からは不要に見えて実は依存先の挙動に賭けている記述は書く。書かないと「単純化」で消される。
- **書き手を主語にした弁明**: 「〜と判断した」「〜の方が安全なので」。判断の結果はコードに現れている。同じ内容でも、主語を対象に移して「何をすると何が起きるか」の制約に書き換えるなら残す。

コメントで不明瞭なコードを弁解しない。書きたくなったら、まずコードを直せないか考える。明瞭なコメントが書けないのは、コード側が複雑すぎる兆候である。

### 出典 — 成果物の外側にある文脈を絶対に持ち込まない

成果物は、会話・資料・タスク管理を一切見ていない人が単体で読む前提で書く。書く直前に自問する: この文は、この会話を見ていない人にとって意味があるか。

- 書かない: 外部にある出典やそこから来た動機 (調査資料・設計資料・チケット・会話で決まった経緯、「〜と判明したので」「〜の是正のため」)。読み手が共有していない内輪の呼称 (マイルストーン名、フェーズ番号、社内の略称)。
- 書く: その変更が何を可能にし何を防ぐか、従来何ができなかったか。変更そのものから読み取れる事実だけ。
- 例外: 恒久的な技術参照 (仕様・RFC・ADR・バグ報告) へのリンクは張ってよい。ただしリンク先が読めなくても意味が通るよう、要点は本文に書く。
- 例や説明に使う固有名は、その成果物のスコープの内側から取る。依存される側の記述に、依存する側の固有名を持ち込まない。

### 配置 — 優先順位: 型 ≻ code comment ≻ doc comment

- 型で表現できるもの (型・単位・制約) は型で表現する。コメントは腐るが型は腐らない。
- 手続き的な why は doc comment ではなく実装箇所の code comment に書く。
- doc comment / docstring は sparse に保ち、本当に有益なものだけ残す。

## PR

- 作業 branch には勝手に push してよい。
- `gh pr create --assignee @me` で自分を assignee にする。

### title

何をしたかを1行で言い切る。差分を開かなくても内容が分かること。対象と結果の両方を入れ、「〜の修正」「〜の対応」のようにどちらも分からない題を付けない。

### description

レビュアーが判断を下すのに要る事実だけを、次の順に置く。

1. **TL;DR** — 何を変えたか、なぜか、最も気にされる影響。
2. **背景** — 何が問題だったか。図・表で示す。自明なら省く。
3. **変更内容** — 差分と対応させる。コミットが増えたらここも増やす。
4. **懸念** — 下表の名前をそのまま見出しにする。
5. **代替案** — 採らなかった案と理由。検討していなければ省く。

| 変更種別         | 懸念の見出し       | 中身                                                                       |
|------------------|--------------------|----------------------------------------------------------------------------|
| 機能開発         | 互換性・破壊的変更 | 既存の呼び出し元が壊れないか                                               |
| 負荷試験・性能   | 負荷への影響       | アクセスパターン変化で負荷が減って検証にならない、逆に増えて別物になる、等 |
| データ移行・削除 | データ安全性       | 消えないか、戻せるか                                                       |
| リファクタ       | 挙動の同一性       | 外部から見た挙動が変わっていない根拠                                       |

- **短さを最優先する**。伝えたいことが多いときほど、書き足すのではなく削る。分量は行数ではなく、レビュアーが判断に使わない事実が残っていないかで測る。
- 調査の経緯、丁寧な言い換え、前置きは書かない。
- レビュー中に差分は変わる。desc が今の差分を説明しているか、更新のたびに読み直す。

## Sandbox

- ユーザからの指示を完遂するのに sandbox 無効化が必要な場合は、そのツール実行時のみ sandbox を無効化すること。

## 調査・提案資料

ユーザからのテキストではなく HTML 形式での説明を求められた場合、下記要点に従って作成せよ。

- **自己完結 HTML で書く**。図はインライン SVG、スタイルはインライン CSS で、外部 CDN (mermaid 等) に依存しない。sandbox / offline でもブラウザで開けるようにするため。
- **human-readable な図・表で伝える**。複雑な機序は文章の羅列ではなく、読み手が直観的に掴める図・表に落とす (記法の予備知識を要する表現は避ける)。
- **コード参照は permanent link で張る**。branch 名や `HEAD` のような流動的なポインタは避け、URL単体で常に同じコード・行範囲を参照できる不変の識別子（commit hash や tag 等）を埋めること。
    - **URL形式:** `https://<github-domain>/<org>/<repo>/blob/<immutable-ref>/<path>#L<start>-L<end>`
    - リンク範囲は示したい箇所に合わせる。関数全体でも、関数内の一部の行範囲 (`#L<start>-L<end>`) でもよい。
    - 識別子 (関数名・テーブル名) そのものをリンクテキストにするとフレンドリー。
- **A4 印刷に対応させる** (`@page` / `print-color-adjust: exact`)。
- **出力先:** `~/tmp/docs/<repo-name>/<YYYYMMDD>_<topic>.html`

※ `<github-domain>`, `<org>`, `<repo>`, `<project-root>` は、現在作業中のプロジェクト環境に合わせて適宜置き換えること。
