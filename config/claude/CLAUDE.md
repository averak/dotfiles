# Global Conventions

## 変更方針

- ユーザの依頼に必要な範囲だけを変更する。無関係な cleanup、refactor、文章の整形を混ぜない。
- 依頼で変更する対象を除き、既存の識別子、公開契約、データ形式、呼び出し規約を維持する。
- 既存コードは、用語と統合上の制約を確認するために参照する。実装とコメントの品質基準にはしない。
- リポジトリに明示された規則に従う。規則と制約を満たす実装が複数ある場合は、明確で単純な実装を選ぶ。
- 見た目を揃えることだけを目的に、不要な複雑さ、責務の混在、曖昧な名前、検証不足を複製しない。
- 指示されていない依頼、約束、今後の作業を追加しない。

## Sandbox

- ユーザの指示を完遂するために sandbox の無効化が必要な場合は、必要な tool 実行に限って無効化する。

## 自然言語の記述

この節は、code comment、doc comment、docstring、docs、commit message、PR title、PR description など、自然言語で書く成果物に適用する。

### 目的と読み手

- 内容を選ぶ前に、成果物ごとに1つの目的と主な読み手を定める。主な読み手の前提知識と、読後に得る情報または実行できる操作も定める。
    - 目的に寄与しない内容または主な読み手が必要としない内容は、削除するか別の成果物に分ける。
- 複数段落の文書では、冒頭に目的と対象範囲を書く。
    - 読み手または前提知識が自明でない場合は、冒頭に明記する。
    - 対象外の事項は、読み手が対象だと考え得るものだけを書く。
- 長い文書では、結論または重要な要点を冒頭に要約する。
    - 冒頭の要約と本文の詳細に必要な重複は削除しない。
- 正確性を維持したうえで、完全性と詳しさを目的と読み手に合わせる。

### 言語と語彙

- リポジトリに言語または形式の規則がある場合は、その規則に従う。既存の文章は、内容と品質の基準にしない。
- リポジトリに言語の規則がない場合は、日本語で書く。
- 対象を指す語は、コードベース、仕様、チームが使っている語から選ぶ。
    - 候補が競合する場合は、リポジトリに明示された規則、仕様上の用語、公開された識別子、チームで合意された語、コードベースで一貫して使われている語の順に優先する。
    - 識別子、型名、仕様上の用語は翻訳せず、そのまま使う。
    - 既存の語がない場合は、識別子を使うか、対象の動作を普通の言葉で説明する。
    - 造語と独自の訳語は作らない。
- 同じ対象には同じ語を使う。言い換えで表現を増やさない。
- 同じ語は、送り仮名、英字の大小文字、長音、全角・半角、記号を含め、成果物内で同じ表記を使う。
- 読み手が知らない可能性のある略語、専門用語、前提は、必要になる箇所より前に説明する。
- 例に使う固有名は、成果物が扱う範囲から選ぶ。
    - 依存される側の説明に、特定の呼び出し元だけが知る固有名を持ち込まない。
- 同じ成果物で敬体と常体を混ぜない。
    - 既存の成果物を編集する場合は、敬体または常体を周辺に合わせる。

### 意味の保存

- 文章の表現を調整する場合は、非自明な事実と、それらの因果、条件、対比、例外の関係を保存する。
    - 残りの文章から導けない事実は、冗長とみなして削除しない。
    - 関係が変わる文の分割や統合はしない。
- 短さは、意味を保存した後に最適化する。
- 文の分割、統合、箇条書きへの変換自体を目的にしない。

### 文と段落

- 主語を省略すると対象が曖昧になる場合は、主語を明示する。
- 条件付きの指示は、条件を先に書く。
- 1文では1つの主な論点を扱う。因果、条件、対比、例外の関係を保てる場合は、文を分ける。
- 1文の途中で、表示幅に合わせた改行を入れない。
- 1段落では1つのトピックを扱い、冒頭の1文に結論または論点を書く。
- 冗長な表現を削る。
    - 「〜を行う」は「〜する」と書く。
    - 「〜することが可能である」は「〜できる」と書く。

### 見出し

- 体言止めにする。「〜している」「〜がある」「〜される」で終わらせない。
- 配下の内容を特定できる名前にする。他の節の内容を含む名前にしない。
- 見出しの階層を飛ばさない。
- 見出しを言い換えただけの文を、直後に置かない。

### 情報の構造

情報の関係に対応する構造を使う。

| 情報の関係                   | 構造                       |
|------------------------------|----------------------------|
| 同じ重要度の並列項目         | 同じ階層の箇条書き         |
| 規則の適用条件、例外、具体化 | 親規則の配下にある箇条書き |
| 手順、優先順                 | 番号付きリスト             |
| 独立して適用できる規則群     | 見出し                     |
| 複数の対象を複数の観点で比較 | 表                         |
| 順序、分岐、依存             | 図                         |
| 事象間の因果、条件の説明     | 地の文                     |

- 箇条書きは、情報の関係を示すために使う。
    - 並列な項目は、文法、粒度、語尾を揃える。
    - 見た目を整えることだけを目的にネストしない。
    - ネストだけでは関係を追いにくい場合は、見出しまたは表に分ける。
- 手順では、読み手が実行する操作だけを番号付き項目にする。システムの動作は、その操作の結果として書く。
- 図は、文章や表より関係を追いやすくなる場合だけ使う。
    - Markdown では mermaid を優先する。
    - mermaid で表しにくい場合は、ASCII 図を code block に入れる。
    - 図の題名、結論、図全体に対する注記は図の外に置く。関係を理解するためのラベル、凡例、グループ名は図内に置ける。
    - 同じ内容を表と図の両方で示さない。ただし、出力形式またはアクセシビリティの制約によって一方だけでは情報が伝わらない場合を除く。
    - 図または画像には、同じ要点を伝える代替テキストまたは説明を付ける。
- 箇条書き、表、図だけでは目的または読み方が分からない場合は、必要な前提、観点、理由を直前に書く。
    - 「以下に示す」「次のとおり」のように、構造を予告するだけの文は置かない。
- 箇条書き、表、図から読み取れる内容を、直後の文章でそのまま繰り返さない。ただし、アクセシビリティのために必要な説明を除く。

### 事実と検証

- 事実と確認結果を書く。誇張、感想、測定していない評価は書かない。
- 確認した範囲と確認していない範囲を区別する。
- 計算結果と測定結果は、再計算または再測定できる場合は結果を確認し、その条件を記録する。
    - 結果を確認できない場合は、確認できない理由、条件、確認していない範囲を明記し、出典がある場合は添える。
- 「〜と説明できる」「〜と考えるのが自然」のように、書き手の解釈を地の文に混ぜない。
    - 解釈が必要な場合は、根拠となる事実を先に書き、そこから導ける範囲だけを書く。
- 同じ対象の数値が食い違う場合は、基準日時、定義、測定条件の違いを明記する。
    - 同一時点の値として比較する場合は、対象となる基準日時を揃える。取得日時が結果に影響する場合は、取得日時も揃える。
- 数値には、その数値が示す対象を併記する。
    - 測定条件を知らないと結論が変わる場合は、期間、サンプリング、除外条件を併記する。

### 自己完結性

- 成果物は、定めた前提知識を持つ読み手が、会話、調査資料、タスク管理を見ずに単体で理解できる内容にする。
    - 外部の文脈だけを理由として「調査で判明したため」「指摘の是正のため」と書かない。
    - 対象の問題、制約、変更後の挙動を書く。
    - 読み手が共有していないマイルストーン名、フェーズ番号、社内略称は、必要な場合だけ定義して使う。
- 外部資料を参照する場合は、資料を読まなくても主張が伝わるように要点を書く。
    - 仕様、RFC、ADR、issue、bug report は、補足資料としてリンクできる。

### 出典と参照

- 外部資料から数値または文言を引用する場合は、出典を直接確認する。一次資料を利用できる場合は、一次資料を使う。
    - 出典を直接確認できない情報は、事実として断定しない。
- 出典は、引用または根拠とした内容があるページを指す。一覧やカテゴリのトップを指さない。
    - 引用を書くときに、その文言があるページの URL を同時に記録する。
    - リンクテキストには、資料名またはリンク先を特定できる短い説明を使う。
    - 書き手または想定読者によって意味が変わる場合は、誰が誰に向けて書いた資料かを添える。
- 節や章を参照する場合は、番号だけに依存せず、対象の名前を併記する。

### 保守と確認

- 依頼対象のコード変更によって文書またはコメントが不正確になる場合は、同じ変更で更新する。
- 同じ情報を複数の成果物で重複して管理しない。別の成果物では、情報を管理する箇所へリンクする。
    - 目的と読み手に合わせて要約する場合は、必要な範囲で重複できる。
- 更新対象の文書が不要になった場合は、廃止されたことを明記し、代替となる文書がある場合はリンクする。
- 文書を作成または更新したら、事実の正確性、主な読み手にとっての明確さ、用語と構造の一貫性を確認する。
    - 手順を安全に実行できる場合は、記載した順に実行し、前提条件と結果を確認する。

## コメント

### 役割と配置

- コメントは、コードや型だけでは表現できず、利用または変更に必要な情報がある場合だけ書く。
    - コメントで実装の不明瞭さを補う前に、コードの構造や名前で明確にできないか確認する。
    - 書くべき情報がない場合は、コメントを追加しない。
- コメントの内容は、周辺のコメントではなく、この節の基準で決める。
    - 周辺のコメントは、用語、言語、doc comment の形式を確認するためにだけ参照する。
    - 情報の不足、実装の言い換え、古い内容を踏襲しない。
- 情報は、その情報を必要とする読み手に最も近い場所へ置く。
    - 型、単位、制約を型で表現できる場合は、型で表現する。
    - 呼び出し元が知る必要のある契約は、doc comment に書く。
    - 実装箇所だけに関係する制約と理由は、code comment に書く。

### 書く情報

- エラー条件、空値の扱い、副作用などの非自明な契約
- 不変条件、処理順序、並行性、所有権
- 一見すると不要に見える処理を削除または単純化できない理由
- 依存先の挙動に依存する箇所と、その前提が崩れた場合の影響

### 書かない情報

- 識別子、signature、実装を言い換えただけの説明
- 言語、DB、library を使う人にとって一般的な事実
- 現在の実装を制約しない過去の経緯
    - 過去の経緯が現在の実装を制約する場合は、経緯ではなく現在の制約を書く。
- 依存先の設計そのものの解説
    - 呼び出し側が依存する挙動は、その挙動と前提が崩れた場合の影響を書く。
- 「〜と判断した」「〜の方が安全」のように、書き手を主語にした弁明
    - 判断の説明が必要な場合は、対象の制約と、制約に反した場合の影響を書く。
- subcommand や field の一覧など、コード変更で不整合になる情報

## PR

- 作業 branch には勝手に push してよい。
- PR を作成する場合は、`gh pr create --assignee @me` で自分を assignee にする。

### `title`

- 対象と変更後の状態を1行で書く。
- 「〜の修正」「〜の対応」のように、差分を開かないと内容が分からない表現を使わない。

### `description`

`TL;DR` は必ず書く。それ以外の節は、レビュー判断に必要な場合だけ、次の順序で書く。

| 順序 | 区分         | 書く条件                             | 内容                                     |
|-----:|--------------|--------------------------------------|------------------------------------------|
|    1 | TL;DR        | 常に書く                             | 何を変えたか、なぜ必要か、最も重要な影響 |
|    2 | 背景         | 問題が差分だけでは分からない         | 変更前の問題と、変更に必要な前提         |
|    3 | 変更内容     | TL;DR だけでは差分を説明できない     | 独立した変更単位と、それに対応する差分   |
|    4 | 該当する懸念 | レビュアーの判断に影響する懸念がある | 懸念と、その確認結果                     |
|    5 | 代替案       | 不採用の案がレビュー判断に必要である | 案と不採用の理由                         |

- 背景の関係を文章で追いにくい場合だけ、図または表を使う。
- 変更内容は、commit ではなく独立した変更単位で分ける。
- 懸念ごとに独立した節を作り、見出しには懸念自体の名前を使う。
    - 下表の条件に該当する場合は、表の見出しをそのまま使う。
    - 複数の懸念に該当する場合は、それぞれを書く。

| 懸念の見出し         | 書く条件                              | 内容                                 |
|----------------------|---------------------------------------|--------------------------------------|
| 互換性・破壊的変更   | API、機能、依存関係、schema の変更    | 既存の呼び出し元と利用者への影響     |
| 負荷への影響         | 性能、負荷試験、access pattern の変更 | 負荷の増減と検証条件への影響         |
| データ安全性         | データ移行、更新、削除                | データが失われる条件と復旧方法       |
| 挙動の同一性         | refactor                              | 外部から見た挙動が変わっていない根拠 |
| セキュリティへの影響 | 認証、認可、秘密情報、入力検証の変更  | 公開範囲、権限、信頼境界への影響     |
| 運用への影響         | 設定、deploy、監視、rollback の変更   | 適用手順、失敗時の影響、復旧方法     |

- レビュアーが判断に使わない事実は削る。
    - 調査の時系列、前置き、同じ内容の言い換えは書かない。
    - 数値と検証結果には、判断に必要な条件を併記する。
- レビュー中に差分を変更した場合は、`title` と `description` が現在の差分を説明しているか確認する。

## HTML 形式の調査・提案資料

ユーザが HTML 形式を指定した場合は、次の規則を適用する。

- 外部 CDN に依存しない自己完結 HTML を作る。
    - 図は HTML 内の SVG で実装する。
    - CSS は HTML 内の `<style>` に書く。
- 複雑な機序は、予備知識なしで関係を追える図または表で示す。
- GitHub 上のコード参照には、permanent link を使う。
    - commit hash または tag を使う。branch 名と `HEAD` は使わない。
    - URL は `https://<github-domain>/<org>/<repo>/blob/<immutable-ref>/<path>#L<start>-L<end>` の形式にする。
    - `<github-domain>`、`<org>`、`<repo>` は、現在のリポジトリに合わせる。
    - リンクテキストには、参照対象の関数名、型名、table 名を使う。
    - 参照範囲は、説明に必要な行だけにする。
- A4 印刷に対応する。
    - `@page` を指定する。
    - `print-color-adjust: exact` を指定する。
- `~/tmp/docs/<repo-name>/<YYYYMMDD>_<topic>.html` に出力する。
