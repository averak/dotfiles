# 作業記録と再開

作業の進捗と根拠をファイルに残し、会話履歴だけに頼らず継続・再開できるようにする。明示指定された場合は、所要時間や規模にかかわらず開始時から適用する。

記録だけで終わらず、依頼された作業と必要な検証を進める。適用は依頼範囲や操作の権限を広げず、完了条件を満たしたら終了する。

## 開始時の記録

本格的な調査や実装に入る前に、次の準備を完了する。再開の依頼では新規に作らず、「中断と再開」の手順を使う。

1. 依頼の目的、対象範囲、制約、完了条件を確認する。
2. この作業の既存の計画や記録があれば読み、その保存先を使う。新規の保存先は、ユーザまたはリポジトリの指定を優先する。指定がなければ、`$HOME/tmp/<org>/<repo>/<作業名>/` に作る。
    - `<org>/<repo>` は Git remote などから確認する。リポジトリで分類できない作業は、`$HOME/tmp/<プロジェクト名>/<作業名>/` に保存する。
    - 同名の別作業がある場合は、日時などを加えて区別し、既存の記録を上書きしない。
3. 初期記録を保存する。目的、対象範囲、制約、完了条件、現在の方針、次の作業、作業対象とこの skill の参照先を残す。開始時点で不明なことは未確認として扱う。
4. 保存したファイルを確認し、記録の保存先をユーザに伝えてから、本作業を開始する。

## 記録の構成

- 記録は1ファイルから始めてよい。量が増えたら、再開用の要約、実行記録、証拠を分け、要約から必要な記録を辿れるようにする。既存の設計文書や計画の詳細は複製せず参照する。
- 再開用の要約には、現在の結論や方針、進捗、未確認事項、障害、次の作業と、根拠・関連ファイルへの参照をまとめる。
    - 計画した作業と実行済みの作業、実装済みと検証済みを区別する。
    - TODO は依頼の各項目と対応づけ、その現在の状態を要約にも残す。TODO ツールだけを再開用の記録にしない。
    - 実行中の処理があれば、ジョブ ID などの識別情報、状態、結果の確認方法を残す。
- 認証情報は記録しない。機密情報や大量の結果を保存する場合は、必要な範囲と保存先のアクセス権、Git の追跡対象を確認する。

## 作業中の更新

- 重要な実行結果、発見、判断、進捗の変化をその都度保存し、再開用の要約も現在の状態に合わせる。context compaction (会話履歴の圧縮) の直前や、作業終了時の一括保存に依存しない。
- 実行記録では、実行の目的、実際のクエリやコマンド、実行条件、成功・失敗を含む結果、考察を対応づける。
    - 日時、対象期間、タイムゾーン、パラメータ、データやコードの状態など、結果の解釈や再確認に必要な条件を残す。
    - 既存ツールでクエリや結果を保存できる場合は、その機能を使い、記録から参照する。実行内容を修正して再実行する場合も、過去の実行内容と結果の対応を保つ。
    - 確認した事実と推測・仮定を区別し、結果から分かったことと、まだ判断できないことを残す。
- 重要な判断には理由と根拠への参照を添える。結論や方針が変わった場合は、過去の実行記録を消さず、変更理由を追記する。今後の判断に必要な失敗や棄却した案も残す。
- 依頼が追加・変更・撤回されたら、完了条件、方針、TODO と記録を更新する。実際に完了していない項目を、計画から外しただけで完了扱いにしない。

## 中断と再開

- この作業を継続する間は、後続の会話でも記録を更新する。中断や引き継ぎの際は要約を更新し、作業記録とこの skill の参照先を引き継ぐ。
- 再開時は、この skill と再開用の要約を読み、必要な証拠を参照する。コード、差分、データなど、作業に関係する現在の状態と照合してから続ける。
    - 記録と現状が食い違う場合は、原因を確認して記録と方針を更新する。
    - データやコードが変わっている場合は、以前の検証結果が現在も適用できるか判断し、必要な範囲を再検証する。
    - 実行済み・実行中の処理を確認してから再実行の要否を判断し、重複実行を避ける。
- 記録が見つからない場合は、指定された保存先と引き継ぎ情報を確認する。復元できなければユーザに伝え、確認できた事実と不足している情報を区別する。失われた実行結果や判断理由を推測で埋めない。

## 完了時の記録

- 元の依頼と追加・変更された指示を照合し、結果、検証済みの範囲、未完了事項、残る不確実性を記録して報告する。記録の保存先も示す。
- 完了後も記録を残す。この作業の記録を新しい依頼に自動で流用せず、別作業の証拠や進捗を混在させない。
